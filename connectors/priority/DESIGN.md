# תכנון הפריטים הפתוחים

המשך ל‑`LOGIC.md`. שלושת הפריטים שנותרו לתכנון: (1) איפה נשמרת הלמידה,
(2) הקישור (deep link) לתנועה בפריוריטי, (3) סנכרון חוזר של סטטוס/מספר סופי.

> חלוקת אחריות: ה‑**connector** (MCP) הוא שכבת הגישה ל‑Priority (קריאה/כתיבה).
> ה‑**למידה והסנכרון** חיים בצד **Pay Day** (Firestore + Cloud Functions), כי הם
> מצב מתמשך של האפליקציה. הקונקטור רק מספק את הנתונים מ‑Priority.

---

## 1. איפה נשמרת הלמידה

**המלצה: פרופיל לכל ספק ב‑Firestore (מקור האמת), שמוזרע מ‑Priority ומתעדכן בכל קליטה ובכל תיקון אנושי.** כך גם חוסכים קריאות ל‑Priority (כמו שביקשת).

מיקום: `tenants/{tenantId}/supplierProfiles/{key}`

```jsonc
{
  "vendorNameNormalized": "google cloud",
  "vendorAliases": ["google cloud", "google cloud emea"],
  "prioritySupplierNumber": "213-12",      // SUPNAME — אחרי התאמה/הקמה
  "expenseAccounts": [                       // היסטוריית חשבונות הוצאה
    { "accName": "5100", "accDes": "תוכנה", "count": 8, "lastUsed": "2026-05-01" }
  ],
  "preferredExpenseAccount": "5100",        // תוצאת כלל ההכרעה
  "fieldTemplate": {                         // ברירות מחדל שנלמדו לרישום
    "currency": "USD", "department": "R&D", "vatRate": 0
  },
  "invoiceCount": 8,
  "confidence": 0.9,
  "source": "priority|payday|manual",
  "updatedAt": "<ts>"
}
```

**מתי מתעדכן:**
- *הזרעה*: בפעם הראשונה שספק מזוהה ב‑Priority עם חשבוניות קודמות — קוראים אותן
  (`PINVOICES?$filter=SUPNAME eq '...'&$expand=<line subform>`), מחלצים חשבונות
  הוצאה + שדות, ובונים פרופיל.
- *כל קליטה*: מעדכנים `count/lastUsed`. אם מנהלת החשבונות שינתה ידנית → רושמים את
  התיקון (לומדים גם מתיקונים).

**מפתח הזיהוי:** לפני התאמה — שם ספק מנורמל; אחרי שמכירים את ה‑`SUPNAME` — זיהוי
מדויק לפיו.

**כלל הכרעה ל‑`preferredExpenseAccount`:** הנפוץ ביותר; שובר שוויון = האחרון.
ביטחון נמוך / כמה חשבונות → להשאיר לבחירה אנושית (הטיוטה ממילא מאושרת ידנית).

## 2. קישור (deep link) לתנועה בפריוריטי

**מטרה:** במסך קליטת החשבונית מוצג מספר התנועה כקישור — לחיצה פותחת את מסך
התנועה בפריוריטי.

**מה שומרים על החשבונית ב‑Pay Day** (מתוך תגובת ה‑POST שיוצר את הטיוטה):
- `priorityTransactionNumber` — מספר התנועה (T... בטיוטה).
- `priorityDocKey` — המפתח היציב של המסמך (IVNUM + SUPNAME, או מזהה ה‑autonumber
  הפנימי). **לא** המספר המוצג, כי הוא משתנה ב‑finalize.
- `priorityLink` — ה‑URL לפתיחה.

**בניית הקישור:** הפורמט הרשמי לפתיחת רשומה (מ‑SDK של פריוריטי):
```
priority:priform@FORMNAME:DOCUMENTNUM:COMPANY:TABINIFILE:LANG
```
| חלק | אצלנו |
|---|---|
| `FORMNAME` | `PINVOICES` (חשבונית ספק) |
| `DOCUMENTNUM` | `IVNUM` (מפתח הרשומה) |
| `COMPANY` | נגזר מכתובת ה‑OData |
| `TABINIFILE` | נגזר מכתובת ה‑OData |
| `LANG` | `3` (אנגלית) או קוד עברית |

דוגמה: `priority:priform@PINVOICES:IN26000123:mycompany:tabmob.ini:3`

> **`COMPANY` ו‑`TABINIFILE` נגזרים אוטומטית** מכתובת ה‑OData
> (`.../Priority/{tabula.ini}/{company}`).
>
> ⚠️ הפורמט הזה הוא של **לקוח הדסקטופ** (מפעיל `priform.exe`).

### עבדים דרך הדפדפן (Priority Web) — סוכם
לקוח הווב **לא** משתמש בפורמט `priority:priform`, וקישור‑ווב ישיר לרשומה ספציפית
**אינו מתועד** ב‑SDK הרשמי (הוא תלוי‑התקנה/גרסה). הדרך האמינה לקבל את הפורמט
המדויק: **לפתוח חשבונית ספק אחת ב‑Priority Web ולהעתיק את ה‑URL משורת הכתובת** —
משם נזהה את התבנית (בסיס + איך מקודדים את שם הטופס ומפתח הרשומה) ונטמיע בקונקטור.

הבסיס צפוי להיות כתובת ה‑Priority Web שלכם (למשל `https://<server>/ui/...`),
ובתוכה הטופס ומפתח הרשומה.

**חשבוניות הספק נצפות ממסך "כל החשבוניות".** לכן:
- הקישור צריך לפתוח את מסך "כל החשבוניות" על החשבונית הספציפית.
- ⚠️ שם הישות שמאחורי המסך הזה אולי **אינו** `PINVOICES` (ניחוש נוכחי) — דוגמת
  ה‑URL החיה (או `priority_describe_entity`) תחשוף את השם האמיתי, ואז נעדכן את
  `apInvoice.entity` ב‑`priorityConfig.js`.

## 3. סנכרון חוזר (סטטוס + מספר סופי)

**הבעיה:** אנחנו יוצרים טיוטות (T...). כשהן הופכות לסופיות בפריוריטי המספר משתנה
(26.../25...) והסטטוס משתנה — ו‑Pay Day צריך לשקף את זה.

**מנגנון מומלץ:** Cloud Function מתוזמנת (למשל כל כמה שעות) + כפתור "רענון" ידני.
- שולפת מ‑Priority רק מה ש**השתנה** עם `$since` (יעיל, מכבד את מגבלת הקצב):
  `GET PINVOICES?$since=<lastSyncUTC>` (אם ה‑entity תומך ב‑BPM; אחרת סינון לפי
  תאריך/מפתח).
- מאתרת את החשבונית ב‑Pay Day לפי `priorityDocKey` (היציב!) — **לא** לפי מספר
  התנועה שמשתנה.
- מעדכנת: `priorityStatus` (draft/final), `priorityTransactionNumber` (המספר
  הסופי החדש), `priorityFinalizedAt`, ואת ה‑`priorityLink`.

**שמירת `lastSyncUTC`** לכל לקוח כדי למשוך רק דלתא בכל ריצה.

## 4. ריבוי לקוחות = ריבוי חברות בפריוריטי
**כל לקוח ב‑Pay Day הוא חברה (company) נפרדת בפריוריטי.** ה‑ID של הלקוח שמוגדר
במסך ניהול הלקוחות = **שם החברה** בפריוריטי. לכן החיבור הוא **פר‑לקוח**, לא גלובלי.

מבנה כתובת ה‑OData:
```
https://{server}/odata/Priority/{tabula.ini}/{COMPANY}
                                              └── ה-ID של הלקוח (משתנה פר-לקוח)
```
- חלקים **משותפים** לכל הלקוחות (אותה התקנת פריוריטי): `server`, `tabula.ini`,
  משתמש ה‑API + סיסמה.
- חלק **פר‑לקוח**: `COMPANY` — נשלף מהגדרת הלקוח במסך ניהול הלקוחות.
- הקונקטור בונה את כתובת הבסיס דינמית לכל פעולה לפי החברה של אותו לקוח.

**השלכות:**
- "כל החשבוניות" מציג רק את חשבוניות אותו לקוח — כי כל חברה היא בסיס נתונים נפרד,
  אז הסינון מתקבל "בחינם" מעצם החברה.
- מספר התנועה (T... → 26.../25...) עוקב פר‑חברה — פריוריטי מנהל את המונה לכל חברה.
- הקישור (deep link) ישתמש ב‑COMPANY של אותו לקוח.
- **שינוי קוד נדרש:** במקום `PRIORITY_BASE_URL` יחיד — להפריד ל‑`server` +
  `tabula.ini` + `credentials` (env), ולקבל `company` פר‑פעולה (מ‑Pay Day).
  הכלים יקבלו פרמטר `company`/`tenant`.

מיפוי ב‑Pay Day (ניהול לקוחות): `tenants/{tenantId}.priorityCompany = "<COMPANY>"`.

## תוספות למודל הנתונים של Pay Day (invoices)
| שדה | תיאור |
|---|---|
| `priorityTransactionNumber` | מספר התנועה (T... → 26.../25... אחרי סופי) |
| `priorityDocKey` | מפתח יציב לאיתור הרשומה ב‑Priority |
| `priorityStatus` | `draft` / `final` |
| `priorityLink` | קישור לפתיחת התנועה |
| `priorityFinalizedAt` | מתי הפכה לסופית |
| `expenseAccount` | חשבון ההוצאה שנבחר/נלמד |
| `balanceDate` | תאריך המאזן בתנועה (קובע את שנת המס של המספר הסופי) |

## כלל תאריך המאזן (balance date)
תאריך המאזן בתנועה — שהוא שקובע את שנת המס במספר הסופי (25.../26...):
- חשבונית מ**החודש הנוכחי או הקודם** → תאריך המאזן = **תאריך החשבונית** (אוטומטי).
- חשבונית **ישנה יותר** → **מנהלת החשבונות מזינה** את תאריך המאזן ידנית
  (לא מציבים אוטומטית — מבקשים קלט).

## החלטות/מידע — סטטוס
1. ✅ עובדים דרך **הדפדפן (Priority Web)**. ⏳ נותר: **דוגמת URL אמיתית** של
   חשבונית ספק פתוחה בווב, כדי לבנות את תבנית הקישור.
2. ✅ הסנכרון יהיה **מתוזמן + רענון ידני**.
3. ✅ תאריך המאזן לפי הכלל למעלה (לא תמיד תאריך החשבונית).
4. ✅ כל לקוח = **חברה נפרדת** בפריוריטי; חיבור פר‑לקוח לפי ה‑COMPANY מניהול
   הלקוחות. ⏳ נותר: לרפקטר את `priorityClient` לחיבור פר‑חברה.
