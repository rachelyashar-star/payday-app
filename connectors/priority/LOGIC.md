# לוגיקת הקליטה ל‑Priority — מסמך אפיון

מסמך זה מסכם את הלוגיקה המוסכמת לקליטת חשבוניות מ‑Pay Day ל‑Priority ERP דרך
ה‑MCP connector. הוא משקף את ההחלטות מהשיחה ומשמש אפיון לקוד שב‑`connectors/priority`.

> **שלב נוכחי (rollout):** הכל נכנס ל‑Priority כ**טיוטה** בלבד — בלי finalize ובלי
> תנועות יומן סופיות. פתיחת ספק היא ידנית עם תצוגה מקדימה ואישור. אחרי שהלוגיקה
> תוכח ותדובג נעבור לאוטומציה (דגלים ב‑`src/priorityConfig.js → behavior`).

## עקרון על
**קליטת החשבוניות נפרדת לחלוטין מאישורי התשלום.** הטריגר הוא פעולת
"קליטה מהירה", לא `clientApproved`.

## הזרימה (צעד‑אחר‑צעד)

### 1. דדופ בתוך Pay Day (קודם כל — לחיסכון בקריאות)
- כל חשבונית נכנסת נבדקת מול Pay Day עצמו.
- אם כפולה → מסומנת ככפולה, וכל הפרטים נלקחים מהחשבונית הקיימת ב‑Pay Day
  (לא פונים ל‑Priority).
- **מפתח דדופ מומלץ: ספק + מספר חשבונית** (`invoice_number`), לא סכום.

### 2. חשבונית חדשה → בדיקת ספק + דדופ ב‑Priority
- קריאה ל‑Priority: האם הספק קיים? (`priority_find_supplier`)
- אם הספק קיים → לבדוק שהחשבונית לא קלוטה כבר ב‑Priority
  (`priority_check_invoice_exists`, מפתח SUPNAME + IVNUM).
- אם **כבר קלוטה** ב‑Priority → לקרוא איך נרשמה (חשבון הוצאה, שדות) וללמוד מזה
  לחשבוניות הבאות מאותו ספק. כדאי גם לסמן אותה כקלוטה ב‑Pay Day ולקשר.

### 3. ספק קיים, חשבונית לא קלוטה → רישום עם למידה
- אם יש חשבוניות קודמות מאותו ספק → להשתמש בלמידה כדי לזהות את **חשבון ההוצאה**
  לרישום, ולחלץ את השדות הרלוונטיים מחשבוניות דומות קודמות → רישום נכון.
- **כלל הכרעה** (כשיש כמה חשבונות הוצאה היסטוריים): לבחור לפי השכיח/האחרון;
  כשהביטחון נמוך — להשאיר לאישור אנושי (הטיוטה ממילא עוברת אישור מנהלת חשבונות).

### 4. ספק לא קיים → הקמת ספק + חשבון הוצאה
- **הקמת ספק חדש** (תצוגה מקדימה → אישור):
  המספר ממשיך מהספק האחרון במערכת — שומרים את הקידומת ומוסיפים 1 לרץ
  (`213-12` → `213-13`). מומש ב‑`supplierNumbering.js`.
- **בחירת חשבון הוצאה:**
  - דרופדאון עם חיפוש בין חשבונות ההוצאה הקיימים (`priority_search_expense_accounts`).
  - או כפתור "פתיחת חשבון הוצאה חדש":
    - מנהלת החשבונות מקלידה **מספר ידני** (לא אוטומטי).
    - בודקים אם פנוי (`priority_check_account_available`).
    - פנוי → פותחים (`priority_create_expense_account`).
    - תפוס → חוסמים ומציגים **"מספר החשבון תפוס"**.
- "ללמוד" את הספק להמשך (שמירת הקשר ספק → חשבון הוצאה).

### 5. מספר תנועה + קישור חזרה ל‑Priority
- תנועת טיוטה נוצרת ע"י Priority עם מספר שמתחיל ב‑**T**, עוקב למספר T האחרון
  של אותו לקוח. **Priority מייצר את המספר — אנחנו רק קוראים אותו מתגובת ה‑POST.**
- מספר התנועה חוזר למסך קליטת החשבונית כ**קישור** — לחיצה פותחת את מסך התנועה
  ב‑Priority.
- כשהתנועה הופכת לסופית ב‑Priority, המספר משתנה לפי **שנת המס** של הרישום:
  2026 → מתחיל ב‑`26`; חשבונית על שנה קודמת (2025) → מתחיל ב‑`25`.
  - לכן קריטי להציב על הטיוטה את **תאריך החשבונית הנכון**, כדי שתיפול בשנה הנכונה.
- **שלב סנכרון חוזר (לא הוגדר עדיין במלואו):** כיוון שאנחנו יוצרים רק טיוטות,
  צריך תהליך שמרענן ב‑Pay Day את מספר התנועה והסטטוס כשהטיוטה הופכת לסופית.

### 6. חשבונית ששולמה באשראי
טרם הוגדר — להשלמה בהמשך.

## עקרונות רוחביים
- **"למידה" = לשמור ב‑Pay Day את המזהים של Priority** (מספר ספק `SUPNAME`,
  חשבון הוצאה, מזהה תנועה) — כך ההתאמות הופכות מדויקות והקריאות פוחתות.
- מגבלות Priority: 100 קריאות/דקה, ספירת טרנזקציות (חבילות 10K/חודש) — לכן בודקים
  בתוך Pay Day קודם ולא מבצעים כתיבות מיותרות.
- **אימות שמות:** שמות הישויות/שדות (`PINVOICES`, `SUPPLIERS`, `ACCOUNTS`, …)
  מרוכזים ב‑`src/priorityConfig.js` וצריכים אימות מול ההתקנה האמיתית
  (`priority_describe_entity`).

## מצב המימוש בקוד
| חלק | סטטוס |
|---|---|
| חיפוש ספק | ✅ `priority_find_supplier` |
| הקמת ספק (תצוגה מקדימה→אישור, מספור עוקב) | ✅ נבדק ביוניט‑טסט |
| חיפוש/בדיקת‑זמינות/פתיחת חשבון הוצאה | ✅ |
| דדופ חשבונית ב‑Priority | ✅ `priority_check_invoice_exists` |
| יצירת חשבונית ספק כטיוטה | ✅ `priority_create_supplier_invoice` |
| למידה מחשבוניות קודמות | ⏳ לתכנון (איפה נשמר: Pay Day vs נגזר חי) |
| מספר תנועה + deep link | ⏳ לתכנון (צריך כתובת UI של Priority) |
| סנכרון חוזר לסטטוס/מספר סופי | ⏳ לתכנון |
| חשבונית באשראי (סעיף 6) | ⏳ לא הוגדר |
